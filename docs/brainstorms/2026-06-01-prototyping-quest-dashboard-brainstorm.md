# 프로토타이핑 퀘스트 대시보드 브레인스토밍

## 무엇을 만들 것인가

현재 Bro-exile은 기본 생존 루프, 보상 선택, 상점, 자동 무기, 간단한 Godot UI가 이미 돌아간다. 하지만 게임이 러프하게 넓어져 있어서 “오늘 무엇을 검증했고, 다음에는 무엇을 고치면 되는지”가 한눈에 들어오지 않는다.

이번 정리의 목표는 게임을 더 복잡하게 만드는 것이 아니라, 프로토타이핑을 **작은 검증 퀘스트**로 나누는 것이다. 각 퀘스트는 목적, 플레이어에게 기대하는 감정, 완료 보상, 통과 기준을 가진다. 사용자는 `todos/README.md`에서 전체 판을 보고, 개별 퀘스트 파일에서 구체적인 할 일을 확인한다.

2026-06-01 사용자 피드백으로 P1 목표를 다시 잡았다. P1은 위험/보상이나 계약 카드의 재미를 검증하는 단계가 아니라, **라운드 5까지 플레이 가능한 전투 게임**을 만드는 단계다. 보상, 계약, 빌드 선택은 P1 이후로 미룬다.

## 현재 문제

- 구현된 기능은 많지만 검증 질문이 기능별로 붙어 있지 않다.
- “재미있다/아니다”가 너무 큰 질문이라 다음 작업으로 쪼개기 어렵다.
- 계약 카드, 팩 클리어, 광산 정체성, UI 검증, 에셋 적용이 같은 우선순위처럼 보인다.
- P1의 목표와 이후 시스템 실험 목표가 섞이면, “플레이 가능한가”를 확인하기 전에 “깊이가 있는가”를 묻게 된다.
- 플레이테스트 결과를 쌓아 두는 형식이 아직 없다.

## 접근 A: 문서형 퀘스트 보드

Markdown 기반으로 대시보드와 퀘스트 파일을 둔다. `todos/README.md`는 현황판이고, `todos/001-ready-p1-...md` 같은 파일은 개별 퀘스트 카드다.

장점은 바로 시작할 수 있고, 에디터/GitHub/Codex 어디서든 읽힌다는 점이다. 단점은 자동 집계나 클릭형 UI는 없어서 사람이 상태를 갱신해야 한다.

## 접근 B: Godot 내부 개발자 대시보드

게임 실행 중 별도 개발자 화면을 띄워 현재 실험, 지표, 다음 퀘스트를 보여준다.

장점은 플레이테스트와 검증이 한 화면에 붙는다. 단점은 지금은 대시보드 자체 구현이 또 하나의 기능 작업이 되어, 프로토타이핑 정리보다 개발량이 커진다.

## 접근 C: 정적 HTML 대시보드

`docs/` 아래 HTML/CSS 대시보드를 만들고, 퀘스트 파일과 수동으로 동기화한다.

장점은 한눈에 보는 느낌이 가장 강하다. 단점은 Markdown 퀘스트와 정보가 이중화되기 쉽다.

## 추천

1차는 접근 A로 간다. 지금 필요한 것은 예쁜 관리 도구가 아니라 **검증 가능한 작업 단위**다. Markdown 퀘스트 보드가 잘 맞으면 이후에 Godot 내부 개발자 대시보드나 정적 HTML 보드로 승격할 수 있다.

## 핵심 결정

- 프로토타이핑의 P1 메인 퀘스트는 “5라운드 동안 서로 다른 적 패턴이 누적되는 플레이 가능한 전투 루프가 있는가?”로 둔다.
- 계약 카드 기반 위험/보상 루프는 P1 이후의 P2 후보로 내린다.
- 사이드 퀘스트는 기능 구현보다 검증 질문을 중심으로 쪼갠다.
- 각 퀘스트는 `목표`, `플레이어 감정`, `완료 보상`, `통과 조건`을 가진다.
- 퀘스트 상태는 `ready`, `pending`, `complete`로 관리한다.
- 대시보드는 `todos/README.md`를 기준 화면으로 삼고, 기획 목차에서 바로 연결한다.

## 열린 질문

- P1 각 라운드 길이는 몇 초가 적당할까?
- 라운드 사이 보상/상점은 P1에서 완전히 끌까, 아니면 임시 고정 회복만 둘까?
- 퀘스트 보드가 충분히 편하면 Markdown만 유지할까, 아니면 나중에 Godot 안에 개발자 대시보드를 넣을까?
- 플레이테스트 지표를 수동으로 기록할까, 아니면 `--smoke-playtest` 출력에 5라운드 통과 여부를 붙일까?
